Small local models better at medicine.

A small AI model — small enough to run on your own laptop — is not reliable enough to read medical notes on its own. alkor is the layer that makes it reliable enough to be useful.

An orchestration layer between your prompt and local inference. It manages context, constrains the model, and checks its work.

One patient, start to finish. Everything that follows is output from a real run on this machine.

Alkor is the faint companion of Mizar. For centuries, resolving the pair was a test of eyesight — it told you whether your instrument was good enough. A corpus of cases that discriminate does the same job.

The premise

The model is the weakest part. Build around it.

A 4B model is not a clinician. You cannot fix that by explaining more.

Small models fail in four predictable ways. Each one has a fix that does not involve trusting the model.

It will miss findings, invent them, and get arithmetic wrong — all in the same confident voice. The instinct is to write a longer prompt. That is the one move that reliably makes it worse.

What goes wrongWhat alkor does about it
it makes things up Every fact has to quote the note. No quote, no output.
it is bad at arithmetic The maths is done in code. The model's own numbers are thrown away.
it will not admit doubt "Nobody checked" is an answer it is allowed to give — and is scored on.
it gets lost in long instructions It is asked one short question at a time, never everything at once.
The model…alkor's answer
invents findings Every reading carries a verbatim quote, checked by a second model. Unquoted readings never reach output.
cannot do arithmetic Shock index, MAP and pulse pressure are recomputed in code. The model's own numbers are dropped, not reconciled.
will not say "I don't know" "Normal" and "nobody looked" stay distinct. Declining is scored, not excused.
has a short attention span Every instruction competes with the patient for the same window. So no call is asked more than one question.

None of this makes the model smarter. It makes the model's answers checkable — and throws away the ones that fail the check.

alkor does not change the weights, and it does not write a bigger prompt. It keeps each context small, makes the output checkable, and reports nothing rather than something plausible.

The patient synthetic packs/clinical/notes/sh-01-septic-classic.note.txt

Eight sentences, no structure, no labels.

62-year-old male, hypotensive for 90 minutes. BP 78/38. Heart rate 118 bpm. Warm peripheries. Jugular venous pressure normal to low. Capillary refill brisk. Bounding pulse. Lung examination not performed.

This patient is not real. The note was written for testing — no record was copied, edited or paraphrased to make it.

Written for the corpus, not derived from any real record. The pack directory is the likeliest place for patient data to reach a public repository, and there the mistake cannot be taken back.

Hold on to the last sentence. Lung examination not performed is not a finding — it is the absence of one. Watch where it ends up.

The map

Four steps. Only two of them use AI.

One run, four steps — and two of them never touch a GPU.

read the note pulls the facts out of the prose AI
check the numbers recomputes the maths, checks each quote code
re-read the quotes a second AI, to catch invented findings AI
write the summary prints only what survived code
extract gemma-4-E4B · port 8081 260 s model
verify-derived code · no GPU 250 ms rule
verify-source a second model · port 8085 121 s model
assess code · renders the ending 0.6 ms rule

this run, on a 12-core Ryzen 5 5500U with no GPU offload

The two code steps take milliseconds and cannot invent anything. The two AI steps are where the time goes — and where the risk is, which is why each one is checked by something that is not an AI.

If a check fails, the run stops and names the step that stopped it. It never prints a verdict over a failed check.

The vocabulary, in full.

Run
one execution, one input, one run id
Workflow
the recipe — an ordered list of steps
Step
one entry in it

A failing step stops the workflow and returns what it has. No retry, no fallback, no circuit breaker — but the final step runs on every exit, because a refused run is when a caller most needs a sentence.

Each step names its own server, so four steps may cross four models. They load one at a time: the machine is the constraint.

The main idea Inside step 1 — orchestration

Each question starts with a blank page.

Every pass starts from an empty context.

Reading the note is not one big request. alkor asks a few small questions in sequence, and each one starts fresh — the model never carries clutter from the last question.

"extract" is not one model call. A rule picks the questions; each question gets its own call. No call sees another call's prompt.

the obvious wayone big prompt

One instruction covering every question you might ask. It fills about three quarters of everything the model can hold — before the patient is even mentioned.

The model then has to find the relevant paragraph in its own instructions, and a small model is bad at that.

alkorone question at a time

Each question is sent on its own, with just the note attached — around a tenth as much text. Nothing accumulates between questions.

Between the questions, ordinary code does the arithmetic and decides which question to ask next. The model is never asked to do either.

This is most of why it works. A small model is not just forgetful — it gets worse the more you tell it at once.

pass runs on prompt it is sent what it answers
vitals-first model 4,799 chars the numbers, with the words they came from
calculations rule — MAP 51.3 · shock index 1.51
route rule — shock-suspicion (0.92) → run these two
shock-extraction model 1,939 chars the five bedside findings
shock model 12,584 chars the category, and what supports it

Each model call is exactly two messages: its own prompt, and the 204-character note. Nothing accumulates. The largest context any call sees is ~3,200 tokens.

One prompt that could answer every question in the pack would run 103,912 characters — about 26,000 tokens, or 79% of this model's 32k window spent before the patient is mentioned.

Splitting is also what makes the prompt cache work: every pass sends a byte-identical prefix, so llama.cpp re-evaluates almost none of it.

The model was never asked for 1.51 — only for 78 and 118, with the words it read them from. The arithmetic happens once, in one place, and everything downstream reads the answer rather than re-deriving it.

Step 3 — verify-source a second model

A different model reads the note back.

Step 2 proved the quotes are in the note. Step 3 asks a separate model whether they say what the extraction claims. It is the invention check, and the most expensive step in the run.

step 3 outputverifier · port 8085
{
  "verified": true,
  "confidence": 1,
  "issues": []
}

Why a whole second model for three fields?

Because a fabricated finding arrives in the same confident voice as a real one, phrased exactly as a clinician would phrase it. Nothing downstream can tell them apart — so something upstream must, and it has to read the source rather than the extraction's account of itself.

If this step returns issues, the run stops and the ending names the step that refused. A verdict is never printed over a failed check.

The decision itself

The diagnosis is a lookup table, not a guess.

The rule is twelve lines of code. The model is graded against it.

Two findings decide the category: whether the skin is warm or cool, and whether the neck vein is raised or not. That is the whole rule.

JVP normal / lowJVP elevated
skin warm septic ← indeterminate
skin cool hypovolemic cardiogenic

src/profiles/clinical/shock.ts — classify()

Our patient is warm with a low JVP. That cell is the only thing that decided the category.

The fourth cell is unassigned on purpose — a vasodilated patient who is also volume-overloaded is the presentation the bedside cannot separate. The honest output is the name of the ambiguity.

So the table runs in code, not in the model. A lookup the model gets right 95% of the time is worse than just doing the lookup.

The model is still asked the same question, and its answer is compared against the table. That comparison is the score — it tells you whether the model is applying the rule or substituting a hunch.

Nothing is gained by asking a 4B model to do a table lookup, and something is lost: a lookup the model gets right 95% of the time is strictly worse than a lookup.

So the table is the answer key, and the headline number is agreement. High agreement means the table should ship alone. Low means the model is wrong — on this input there is nothing else for it to be. Either way the run says something.

The model earns its place on the residue: where the table abstains, where findings contradict, and why a case is undecidable. A 2×2 can express none of that.

And the honest part. The rule comes from a 2010 bedside study of 68 patients. It got 52 of 68 right — 76%. That is the ceiling, and no software raises it. alkor can make the answer traceable; it cannot make the rule better than it is.

Where the rule comes from. Vazquez et al., J Hosp Med 2010;5(8):471–4 (PMID 20945471). Sixty-eight hypotensive patients; skin temperature and JVP alone placed 52 of 68 correctly — 76%, and the authors called it a pilot. That 76% is the ceiling, and no software raises it.

This last step invents nothing. It only re-prints facts that earlier steps already produced and checked. Where the model wrote words, they appear word for word — never reworded, because once reworded you cannot tell which words were the model's.

Read a speed with more care than a score. Correctness travels between machines; throughput does not.

So the conditions line is read from the server, and nothing gates on it. There is no bench verb, deliberately — llama-server returns its timings unasked, so a measured run and an unmeasured one send identical bytes.

The result that argues for the grammar. gemma-3-4b-it, same weights, same corpus, same question:

free 0 / 88 — 21 cases failed
constrained 88 / 88 detection

And the footnote the harness prints rather than letting you guess: the 0/88 is a format failure. Every reply came back in a ```json fence and nothing parsed. Re-scored with the fence stripped, it is 84/84.

A grammar buys shape, and only where shape is missing. Qwen3-4B's two arms are identical — a model that already emits clean JSON has nothing left to buy.

Where that leaves you

What it is, what it is not, and how to run it yourself.

It is not

a medical deviceand not a substitute for a clinician
proof of anythingthe test cases are written, not patients
an AI modelit is the layer built around one

A perfect score here shows two things, and only two: a published bedside rule was applied faithfully, and the model said so when the rule did not reach far enough.

a medical devicenor clinical decision support
validation evidencenothing here is for a regulator
an eval frameworkone assembly feeds eval and production
an inference serverllama.cpp does that; alkor is the layer above

The corpus contains no patients — only payloads written to exercise distinct routes through a rule. A perfect score shows two things: the heuristic was applied faithfully, and the model declined where it did not reach. Nothing else.
